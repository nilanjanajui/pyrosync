# Architecture & Technical Decisions Log

This document records architectural, data, and design decisions made throughout the development of PyroSync.

---

## 2026-11-14 — Initial Project Architecture & Scaffolding

### DEC-001: Separation into `frontend/` and `backend/` Folders
- **Context**: The master prompt initially specified `web/` and `pipeline/`. The user requested explicit frontend and backend folder naming.
- **Decision**: Renamed `web/` to `frontend/` and `pipeline/` to `backend/`.
- **Consequences**: `netlify.toml` / `vercel.json` and all repository scripts reflect `frontend/` as the root web directory and `backend/` as the Python data processing and validation package.

### DEC-002: Static-First Architecture with Client-Side Typed Array Computation
- **Context**: Hotspot and grid data spanning 22 years (2000-11 to 2021-12) over 4,527 cells in California requires interactive filtering by arbitrary user AOIs.
- **Decision**: Pre-aggregate data to cell-months (10 km equal-area EPSG:6933 grid cells) in columnar JSON format. The frontend unrolls these records into dense flat `Float32Array` buffers (254 months × 4,527 cells). Full-AOI recalculation is achieved in < 10 ms via typed array summation without requiring an online database or server backend.

### DEC-003: Hotspot Shards for Download Performance
- **Context**: Hotspot-level records (~1 million detections) would bloat the initial page load if loaded upfront.
- **Decision**: Partition hotspot detection records into annual quantized JSON shards (`frontend/public/datasets/hotspots/<year>_<sensor>.json`) indexed by `hotspots/index.json`. The frontend lazy-loads only the shards required for the user's selected date range when a CSV download is requested.

### DEC-004: Strict Contract Mirroring via JSON Schema and Zod
- **Context**: Data payloads generated by Python must match frontend loader expectations with zero drift.
- **Decision**: Python JSON Schemas in `backend/pyrosync/schemas/` define the source of truth, mirrored by Zod schemas in `frontend/src/datasource/schema.ts`. CI runs a contract test validating that `pyrosync synth` output parses cleanly through the frontend loader.

### DEC-005: Hosting & Deployment on Vercel
- **Context**: The frontend is a static Vite SPA requiring SPA route rewrites and asset caching rules.
- **Decision**: Configure `frontend/vercel.json` with SPA rewrites to `/index.html` and explicit cache headers (no cache for `manifest.json`, aggressive immutable caching for static versioned datasets).

## 2026-11-14 — Milestone 1, 2 & 3: Contract Update, Map AOI & Burn Calendar

### DEC-006: Harmonization Data Contract Update (Real Pipeline Alignment)
- **Context**: Colab notebook outputs (Phases 5-7) fit a seasonal ratio model (DJF/MAM/JJA/SON = 3.315/3.175/4.275/4.476 for combined MODIS, and 7.714/5.906/8.145/8.977 for Terra-only era). The previous synthetic contract assumed a single scaling number and missing per-record provenance.
- **Decision**:
  - Updated `harmonization.json` JSON schema and Zod model with `seasonalRatios`, `terraOnlyRatios`, `firstAquaMonth: "2002-07"`, `perMonthSources` (with integer codes 0=observed_viirs, 1=predicted_modis_viirs, 2=predicted_terra_only), `bootstrapCi`, and `uncertainty` containing empirical 5th–95th percentile typical error bands from leave-one-year-out CV.
  - Added integer `source` array to `cell_months.json` harmonized block to track per-record provenance.
  - Set `validation.wape = 0.129`, `validation.forwardTestBias = -0.096`, and cell-level bias warning for low counts.

### DEC-007: Geospatial AOI Snapping & MapLibre Grid Choropleth
- **Context**: Users need to select arbitrary AOIs (statewide, bounding box, or center+radius) and instantly recalculate the aggregated burning series.
- **Decision**:
  - Implemented `FireMap.tsx` using MapLibre GL with Carto Dark Matter basemap (no API key required) and resilient slate-900 offline fallback.
  - Used `promoteId: "id"` and `setFeatureState` for performant cell highlight and Cividis cumulative detection choropleth without re-uploading GeoJSON geometries.
  - Implemented `aoi.ts` with Turf.js for point-in-polygon cell snapping and bounding-box calculations.
  - Added warning banner when AOI area < 500 km² (`isAoiTooSmall`), warning that cell-level predictions are biased at low counts.

### DEC-008: ARIA Grid Burn Activity Calendar & Accessibility
- **Context**: The challenge requires an accessible month × year calendar displaying burning activity, comparing counts against multi-year averages/medians, distinguishing observed from predicted data, and supporting WCAG 2.2 AA.
- **Decision**:
  - Built `BurnCalendar.tsx` adhering to the ARIA Grid pattern with full arrow-key and Home/End navigation (`role="grid"`, `role="row"`, `role="gridcell"`).
  - Used Cividis sequential palette (perceptually uniform and colorblind safe) for counts.
  - Used PuOr diverging palette for the "vs. Median" anomaly view.
  - Distinguished predicted months (pre-2012-02) using CSS hatched overlays (`bg-hatched`) and dashed borders for the Terra-only era, ensuring differences are never communicated by color alone.
  - Highlighted 2012-02 blend boundary with a dedicated sky-blue border and 2012-01 with a partial-month marker.

- **Context**: The user specified a complete design specification transforming the UI from a generic analytics dashboard to a **“scientific command center”** inspired by NASA mission software, oblique satellite reconnaissance telemetry, and high-density geospatial intelligence.

  - Added `HarmonizationModal.tsx` and `ExportModal.tsx` with comment-header CSV export.

## 2026-11-15 — Data-Update Safety & Content Hashing

### DEC-010: Hotspot Shards — Kept Untouched (Legacy Synthetic Data)

- **Context**: `frontend/public/datasets/hotspots/` contains synthetic shards generated by `pyrosync synth` (30 cells, ~10,724 MODIS rows, ~18,295 VIIRS rows, cell indexes 0–29). The real dataset has 4,527 cells and ~279,986 MODIS / ~797,147 VIIRS detections. The shard cell indexes and counts do not match the real `cell_months.json`.
- **Decision**: The shards are **not regenerated** at this time. The main UI does not load them (they are only needed for per-row CSV downloads, which are not yet plumbed to the real hotspot parquet). Modifying them without also re-implementing the full hotspot export pipeline would create an inconsistency between the monthly aggregates and the individual rows, violating the **Reconciliation Invariant** (see `docs/DATA_CONTRACT.md § 2`).
- **Status**: The frontend's lazy-load hotspot path is effectively dead code against the synthetic shards. `pyrosync check` validates their schema but does not check reconciliation (because that requires joining with `cell_months.json`, which is too slow for a schema check).
- **Future Options** (choose one before the next data update):
  1. **Regenerate shards from real data**: Implement `pyrosync export --hotspots` that reads `data/cleaned/phase2/modis_vegetation.parquet` and `viirs_vegetation.parquet`, quantizes them, and writes annual shards. Update the reconciliation test to verify row counts equal monthly aggregates. Estimated effort: 2–3 days.
  2. **Remove shards and relax `check`**: Delete `frontend/public/datasets/hotspots/`, remove `hotspots/index.json` from the required-files list in `cmd_check`, and update `docs/DATA_CONTRACT.md` to mark the CSV-download feature as deferred. The Download button should be hidden or show a "coming soon" message. Estimated effort: 0.5 days.
- **Recommended**: Option 2 (remove) if the Space Apps submission deadline is imminent; Option 1 (regenerate) for a production-quality release.

### DEC-011: Content Hash (datasetHash) for Cache-Busting Safety

- **Context**: Vercel caches `/datasets/*` as immutable for one year. The only cache-buster is `manifest.version` embedded in `?v=` query params. Previously, there was no mechanism to detect if core dataset files were edited without bumping the version.
- **Decision**:
  - `pyrosync export` computes a SHA-256 digest over the five core files (`grid.geojson`, `boundary.geojson`, `cell_months.json`, `harmonization.json`, `validation.json`) and stores it as `manifest.datasetHash`.
  - `pyrosync export` auto-increments the patch version (e.g. `1.0.3` → `1.0.4`) when the hash changes, and keeps the version unchanged when the hash is the same.
  - `pyrosync check` recomputes the hash and fails with a clear error if it differs from `manifest.datasetHash`, catching any manual file edits that bypass `export`.
  - `datasetHash` is **optional** in the frontend Zod schema so that older manifests without the field still parse.
- **Consequences**: Updating the data is now hard to do wrong — the pipeline enforces correct versioning automatically.
